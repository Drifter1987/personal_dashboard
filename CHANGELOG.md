## 2.30.4 — 2026-10-19

An optional encrypted cloud copy, one slot per device: turn it on with a passphrase and each phone seals its own tasks, cards, notes, habits, countdowns, settings and lock record into a slot of its own, so a phone that loses everything can list the slots, pick its own and restore it. Ten devices never overwrite each other, restoring is never automatic, and a deploy still touches no device's data.

## 2.30.3 — 2026-10-19

## 2.30.2 — 2026-10-19

Settings shows when that backup was taken and can restore it on demand.

## 2.27.0 — 2026-10-18

Closing the app and opening it again comes back to where you were, not to Home. The place was always kept twice, but the copy outside the session was honoured for a minute - long enough for a refresh, short enough that a reopened app looked like a first visit - so as the installed app that copy is now trusted for a week, while a plain tab visit still opens on Home. The page that ships also stops allowing inline script wholesale: the bundle computes the SHA-256 of its one script block and pins it in the meta tag and in the response header, so anything injected into the document has a different hash and cannot run. The source keeps the old allowance so the file you open while working still runs, the gate refuses to publish a bundle whose hash is not the hash of the bytes it carries, and the browser contract loads the shipped copy to prove it boots and refuses an injected script. And a passphrase can now seal what used to sit in the clear: the bytes of every attachment and the metals provider key. Both are sealed with AES-GCM under a key derived from the passphrase with PBKDF2-SHA256 (310,000 iterations), and the passphrase itself is stored nowhere - only a random salt and an encrypted check value are. The key lives in memory for the session, so a relaunch locks again, and the passphrase is asked where it is needed rather than at boot: opening a sealed file, or the provider-key field. Files attached before the passphrase was set are sealed in place, removing the protection puts them back exactly as they were, and the settings card says plainly that there is no recovery code, no reset and no way around it.

## 2.25.3 — 2026-10-18

## 2.25.2 — 2026-10-18

Pressing reload keeps the exact place you left, in every section and at every width - including the refresh the app's own button performs, which does not reload the page you are on but opens it again in a new session, and that is the one that used to send you to Home. Three faults met in it. A refresh that starts a new session throws sessionStorage away, and the place lived only there; it is kept in the local store as well now, carrying the address it was taken at and the minute it was taken, and that copy is honoured for a minute - a page left longer ago than that is a new visit, and a new visit still opens on Home. An offset put back too early was clamped by a page that had not finished growing, and stayed clamped, which is a refresh that lands short of your place; it is re-applied whenever the document changes height, for as long as the restore owns the view, so what survives is the number that was recorded. And the record itself was written from a frame, which a view that is not painting never delivers: the pending write was dropped, the guard left set swallowed every later scroll with it, and the reload then put back a position you had already left. It is written from a trailing timer now, which always fires. The browser contract grew to prove all three: every section at three widths, each left at a real offset and reloaded, with the card at the top edge recorded alongside it - a y that comes back to the same number while the content under it has moved is still the wrong place; a run that saves with frames deliberately stubbed out; and a run that comes back in a second session.

## 2.25.0 — 2026-10-17

Every section now ends where its own content ends, and the desktop rows line up. ## 2.19.1 — 2026-10-17

The blank page is fixed, and it was ours. The offline worker precached the shell from /index.html, which the host answers with a 308 to /, so the copy it stored was flagged as a redirect - and a browser refuses a redirected response for a navigation, which is why the address opened to an error page while the site itself was answering 200. The worker now copies the shell from / where there is no redirect, refuses to serve a redirected copy even if an older release left one cached, falls back to the network when the cache itself cannot be opened, and takes over at once when it inherits a cache no page can load, so a browser stuck on the old worker repairs itself instead of waiting for someone to clear site data by hand.
