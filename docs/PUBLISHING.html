Guide · publishing the dashboard

One push, and the site updates itself.

The pipeline is already built: every push to main runs the tests. A release tag on main (for example v2.28.0) then uploads the page to Cloudflare and checks the live site really changed. A plain push publishes nothing. It is waiting on two credentials that only you can create. Add them once, and publishing becomes: commit, push, tag the release, wait a minute, refresh.

Before you start

What you need.

Three things. Two of them you already have.

  • GitHub Desktop installed and signed in as Drifter1987, the owner of the repository. It is already on this machine.installed
  • A Cloudflare login for the account that hosts the site: Drifter_87@live.com. The token you create in step 2 must belong to this account.your login
  • The project folder on this machine, Ghazi_Tools/personal_dashboard, so the first push has somewhere to come from.local
Nothing here moves your address.

The site keeps its project and its home-dashboard-5ma.pages.dev address. No new project is created, no link changes, no QR code needs reprinting. The only new things are two credentials that let GitHub publish on your behalf.

The procedure

Seven steps, in order.

Steps 2 and 3 are the credentials — the only part only you can do. Step 4 proves the whole chain works. Steps 5 to 7 are what you will actually repeat.

  1. 2 min

    Push what is already waiting

    Cloudflare cannot publish a commit that GitHub has never seen, and the pipeline is triggered by the push, not by the file on your disk.

    Open GitHub Desktop, select the personal_dashboard repository, click Push origin, then click Fetch origin a moment later.

    You should see "Last fetched just now", and Push origin with no number beside it. On github.com the commits you just pushed sit at the top of main.

    If the repository is not in the list

    Use File → Add local repository and point it at Documents/AI_Workspace/02_Projects/Ghazi_Tools/personal_dashboard. If a push is refused, click Pull origin first, then push again.

  2. 5 min

    Create one Cloudflare token that can publish

    This is the credential that lets GitHub upload the page. It is scoped to publishing pages and nothing else, on one account.

    In the Cloudflare dashboard:

    1. Click your profile icon (top right) → My Profile → API Tokens.
    2. Click Create Token, then under Custom token click Get started.
    3. Token name: GitHub publishes the dashboard
    4. Permissions: Account · Cloudflare Pages · Edit — the three dropdowns, in that order.
    5. Account Resources: Include · Drifter_87@live.com's Account.
    6. Click Continue to summary → Create Token, then copy the token.

    Cloudflare shows the value once. Copy it straight into step 3 — do not save it in a file, paste it into a chat, or put it anywhere near the repository.

    You should see the token listed under API Tokens, described as Account · Cloudflare Pages · Edit. That description is the proof it will be allowed to publish and not much else.

    If you lose the value before step 3

    A token's value is never shown again. Delete the row and create a new one — a minute of work, and no harm done. Do not try to reuse an older token "to save time": a token with wider permissions than this needs is a bigger problem than the minute.

  3. 3 min

    Give GitHub the token, and the account it belongs to

    The token names what may be done; the account id says where. A Pages token carries no account of its own, which is exactly why both are needed.

    In the repository on github.com: Settings → Secrets and variables → Actions → New repository secret. Add both, one at a time:

    1. Name CLOUDFLARE_API_TOKEN — value: the token you just copied.
    2. Name CLOUDFLARE_ACCOUNT_ID — value: 8660293d5a5646d0131b5edad05d7910

    You should see two entries under Repository secrets, names only — GitHub never displays a value again, and never will. The names must match exactly: a typo here is the single most common reason the next step does nothing.

    If you cannot see Settings

    You are signed in as someone who is not an owner of Drifter1987/personal_dashboard. Sign in as Drifter1987 — repository secrets are not visible to anyone else, which is a feature.

  4. 3 min

    Publish for the first time

    Until now the pipeline has been running and deliberately skipping the upload, saying so each time. With the credentials in place it can do the real thing.

    On github.com open the Actions tab, pick the most recent run of checks, and click Re-run all jobs (top right). The run now sees the secrets.

    You should see three jobs: deploy gate green, release bundle green, and publish the page green with five steps — the last one reading Prove the live site serves the tested bundle. Then open the site's 6th tab, Settings, and the About card shows the version that was just published, not the old one.

    If the publish job says "Publishing skipped"

    The secrets are missing or misnamed — go back to step 3 and check both names character by character. Nothing was published, and the live site is untouched and still working, so there is no rush.

Setup done · now the everyday part

  1. 2 min

    Change something, and publish it

    This is the whole routine from now on. No Cloudflare dashboard, no commands, no credentials to type again.

    In GitHub Desktop: open the Changes tab, type a short summary, click Commit to main, then Push origin. That push runs the tests but does not publish. To release it, tag that commit as the new version (a terminal command: git tag v2.28.0 then git push origin v2.28.0), wait a minute or two, then refresh the site.

    You should see a new run under Actions for your commit, finishing green in about two minutes, and the new version number in the dashboard's Settings → About card.

    If the run is still going

    Two jobs have to finish before the site changes: the tests, then the upload. If the site looks unchanged after five minutes, open the run and read which job stopped — the table below covers what each failure means.

  2. 1 min

    Know how to go back

    A publish you cannot undo is a publish you hesitate over. Cloudflare keeps every previous version, so a bad change is one click from being gone.

    In Cloudflare open Workers & Pages → home-dashboard → Deployments, find the version you want back, and use its menu to roll back to it.

    You should see the site serving the older version within a minute, and the rolled-back deployment marked as the active one.

    If you would rather fix forward

    That is usually better: make the correction, commit, push, tag the new version, and the pipeline publishes it. Rollback is for when you want the old version up now and the fix is not ready yet.

  3. 1 min

    Remember what did not change

    Two things stay exactly as they were, and both surprise people later.

    The address is unchanged, so links, bookmarks and QR codes keep working. The API Worker — reminders, the metals endpoint — is not part of this pipeline and still ships by hand.

    You should see the dashboard working at the address you already use, with reminders still armed. If the Worker were the thing that changed, this pipeline would not have shipped it.

Short version

If you only want the order.

Same procedure with the explaining removed. Not a summary — every step still has to happen.

  • GitHub Desktop → Push origin, so the commits GitHub is missing reach it.
  • Cloudflare → My Profile → API Tokens → Create Token → Custom token; permission Account · Cloudflare Pages · Edit, account included Drifter_87@live.com.
  • Copy the value once; never save it anywhere but the next step.
  • GitHub repo → Settings → Secrets and variables → Actions: add CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID (8660293d5a5646d0131b5edad05d7910).
  • Actions → latest checks run → Re-run all jobs; wait for publish the page to go green.
  • Check Settings → About on the site for the new version.
  • From now on: commit, push, tag the release, wait two minutes, refresh.

Recovery

When it fails.

What each failure actually means, in the order they are likely to appear. In every one of them the live site keeps working: publishing only replaces it after a successful run.

What you see → why → what to do
What you seeWhyDo this
The run says Publishing skippedThe two repository secrets are missing or spelled differently.Re-check both names in step 3, then re-run the job. Names are case-sensitive.
Publish fails with an authentication or permission errorThe token was deleted, or it lacks Account · Cloudflare Pages · Edit.Create a fresh token with that permission, and replace the CLOUDFLARE_API_TOKEN secret's value.
The deploy gate job is redThe tests failed on that commit, so nothing was published — by design.Open the run, read which check failed, fix it in the next commit. The live site is still the last good version.
The run is green but the site is not newLook closely at which jobs ran: a green run with Publishing skipped published nothing.Treat it as the first row: the credentials are the thing to fix.
The site shows the old version for a minute or twoThe edge can serve the previous version briefly after an upload. The pipeline's own check waits for it.Wait, then refresh. If the publish job is green, the change is live.
A push on another branch published nothingOnly a release tag on main publishes. Other pushes run the tests and stop there.Nothing to fix. Merge to main and tag the release when the change is ready to be live.
Reminders or the metals API stopped workingThose live in the Worker, which this pipeline does not touch.Unrelated to publishing. If worker.js changed, the Worker needs its own deploy — ask for it.
A failed run never breaks the live site.

The upload only happens after the tests pass, and Cloudflare switches the live version only after the upload succeeds. A bad change stops at the red job; the site keeps serving the previous version until something better gets through.

Boundaries

What this does not do.

Read this before assuming the setup covers more than it does.

Not covered

The Worker API

Reminders, push notifications and the metals endpoint run in a Worker with its own keys, storage and schedule. It is deployed by hand, and a page publish never touches it.

Not covered

Publishing from another branch

Only a release tag on main publishes. A branch cannot be used to put a draft in front of someone else at the real address — that is deliberate, and it is also why there are no preview links here.

Worth knowing

The tests reach the internet

The gate checks live data sources, so it can occasionally fail for reasons no one here caused. That is a red run to re-run, not a broken site: nothing is published until it is green.

Worth knowing

The credentials are yours to rotate

Deleting the token in Cloudflare stops publishing immediately and leaves the site alone. A new token plus a new secret value restores it — the account id never changes.
