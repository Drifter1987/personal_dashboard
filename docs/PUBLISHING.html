Guide · publishing the dashboard

One push, and the site updates itself.

Right now a commit stays on your computer. The live site is still on v2.10.0 because nothing connects the two. This guide connects them once, in Cloudflare, in about fifteen minutes. After that every change is: commit, push, wait a minute, refresh.

8 steps About 15 minutes, once No API key needed Then ~2 minutes per change
Start at step 1 Just the short version

Steps 1 and 2 were checked on this machine on 2026-10-17. Steps 3 to 6 follow Cloudflare's own documentation and need your Cloudflare login - they are marked as such, not presented as tested here.

Before you start

What you need.

Three things. If one is missing, the step that needs it will not work, so check now rather than halfway through.

  • GitHub Desktop installed and signed in as Drifter1987. It is already on this machine.installed
  • A Cloudflare login that can open Workers & Pages. Use the main account, Drifter_87@live.com.your login
  • The project folder on this machine: Ghazi_Tools/personal_dashboard. It already has the 4 waiting commits.local
Which tool does what — they are not alternatives.

Think of GitHub Desktop as the pen and Cloudflare as the printer. The pen writes the change and sends it to GitHub. Cloudflare watches GitHub and prints whatever it receives. You need both, but you only ever touch one of them: after setup, committing and pushing is the whole job.

Cloudflare is the safer half: it needs no API token, and it can only read the one repository you pick. Nothing secret is copied anywhere.

The procedure

Eight steps, in order.

Steps 1 to 2 are one minute each. Steps 3 to 6 are the setup you only do once. Steps 7 and 8 are what you will actually repeat.

  1. 2 min

    Push the changes that are already waiting

    There are 4 finished commits on this machine that GitHub has never seen. Nothing can publish them until they are there.

    Open GitHub Desktop, select the personal_dashboard repository, then click Push origin in the top bar.

    You should see "Last fetched just now" and no more "Push origin" button with a number. On github.com, the newest commit on main reads Release 2.17.0: settings that open in place, cards that carry files.

    If the repo is not in the list

    Use File → Add local repository and point it at Documents/AI_Workspace/02_Projects/Ghazi_Tools/personal_dashboard. If the push is refused, click Pull origin first, then push again.

  2. 1 min

    Look at what Cloudflare has today

    The existing project was made by uploading files, not by connecting a repository. That kind of project can never be switched to automatic publishing, so it is worth seeing that now instead of hunting for a button that does not exist.

    In the Cloudflare dashboard open Workers & Pages → home-dashboard. Look at the address: home-dashboard-5ma.pages.dev, currently serving v2.10.0.

    You should see no Git connection anywhere on that project's settings page. Cloudflare's documentation says it plainly: a direct-upload project "cannot switch to Git integration later". So step 3 creates a new, separate project.

  3. 3 min

    Let Cloudflare read your repository

    This is the permission step. Cloudflare gets read access to one repository, and nothing else.

    Still in Workers & Pages:

    1. Click Create application, then the Pages tab, then Connect to Git.
    2. Choose GitHub and sign in if it asks.
    3. When GitHub asks which repositories, choose Only select repositories and tick personal_dashboard.
    4. Click Install & Authorize.

    You should see Drifter1987/personal_dashboard in the repository list, and a Begin setup button next to it.

    If the repository is missing

    Open github.com/settings/installations, find Cloudflare Pages, click Configure, and add the repository to its allowed list. Then come back and refresh.

  4. 2 min

    Create the new Pages project

    The name you choose becomes the address, so pick it deliberately. home-dashboard is already taken by the old project, so this one needs a different name.

    Set Project name to home-dashboard-live, set Production branch to main, then click Begin setup.

    You should see a Set up builds and deployments screen with the project name filled in and branch main selected.

    If the name is rejected

    Any unused name works; the address simply follows it. The branch dropdown only lists branches GitHub already has, which is why step 1 comes first.

  5. 2 min

    Fill in the build settings

    Nothing is compiled here: the finished site already sits in the deploy/ folder. The build command is a lock, not a compiler - it refuses to publish if that folder and the page ever disagree.

    Use exactly these three values:

    1. Framework preset: None.
    2. Build command: node _deploy.mjs --artifacts-only
    3. Build output directory: deploy

    Leave Root directory empty. You do not need any environment variables.

    You should see the project summary above the button list that same command and the word deploy.

    If the build complains about npm or dependencies

    Add one environment variable under Environment variables: SKIP_DEPENDENCY_INSTALL set to 1. There is no package.json in this repository, so there is nothing to install.

  6. 2 min

    Save, deploy, and check the version

    This is the moment the live site finally becomes 2.17.0. If the build fails here, nothing changes and the old site keeps working - so this step is safe to try.

    Click Save and Deploy, watch the log, then open the new .pages.dev address it gives you.

    You should see the log end with Success: Your site was deployed!. Then open the dashboard's 6th tab, Settings, and the About card reads v2.17.0.

    If the build fails

    Click the failed build to read its log. The most likely line is deploy/index.html is byte-identical failing, which means the folder on GitHub is older than index.html. Fix it on the computer with node _deploy.mjs --sync, commit, push, and Cloudflare tries again by itself.

Setup done · now the everyday part

  1. 2 min

    Change something, and publish it

    This is the whole routine from now on. No Cloudflare dashboard, no commands, no tokens.

    In GitHub Desktop: open the Changes tab, type a short summary, click Commit to main, then Push origin. Wait about a minute. Refresh the site.

    You should see your commit message in Cloudflare under the project's Deployments tab, and the new version number in the dashboard's Settings → About card.

    If the site still shows the old version

    Check Deployments first: if the newest deployment is still building, wait. If it failed, the old version stays live on purpose. A normal refresh is enough - the service worker deliberately caches nothing.

  2. 1 min

    Decide what happens to the old address

    The new site has a new address. The old one keeps serving 2.10.0 forever unless you do something about it, and any QR code or bookmark you have points at the old one.

    Keep the old home-dashboard project for now, and start using the new address. When you are happy with it, delete the old project in its own Settings → Delete project page — that is permanent, so do it last.

    You should see the new address opening correctly on your phone, and the dashboard showing 2.17.0 there too.

    If you reuse the QR code inside the app

    Open the app's QR & Share card after the move and check which address it encodes. If it still points at the old project, that is worth fixing before you print or share it again.

Short version

If you only want the order.

Same procedure with the explaining removed. Not a summary — every step still has to happen.

  • GitHub Desktop → Push origin, so the 4 waiting commits exist on GitHub.
  • Remember the old project is direct upload and cannot be converted; a new project is required.
  • Cloudflare → Workers & Pages → Create application → Pages → Connect to Git → allow only personal_dashboard.
  • Name it home-dashboard-live, branch main.
  • Framework None, build command node _deploy.mjs --artifacts-only, output deploy.
  • Save and Deploy, then confirm v2.17.0 in the app's About card.
  • From now on: commit, push, wait a minute, refresh.

Recovery

When it goes wrong.

The failures this setup actually produces, in the order they are likely to appear.

What you see → why → what to do
What you seeWhyDo this
The old project has no Git optionIt was created by direct upload, and Cloudflare does not allow converting one.Create a new project (step 3). Do not delete the old one until the new one works.
Cloudflare's repository list is emptyThe GitHub app was installed for a different account, or only for "all repositories" of another login.Open github.com/settings/installations → Cloudflare Pages → Configure → add the repository.
The production branch dropdown is emptyThe branch does not exist on GitHub yet.Push first (step 1), then reload the setup page.
Build fails at deploy/index.htmlThe published folder is older than index.html.node _deploy.mjs --sync, then commit and push the rebuilt deploy/ and zip.
Build fails looking for npm or a lockfileCloudflare tried to install dependencies in a repository that has none.Add SKIP_DEPENDENCY_INSTALL=1 as an environment variable and redeploy.
The site loads but shows an old versionThe newest deployment is still building, or the last build failed and Cloudflare kept the previous one.Open Deployments and read the newest entry's status before changing anything.
Reminders or the metals API stop workingThose live in the Worker, which is a separate deployment from the page.The page moving does not affect them. If the Worker itself changed, it needs its own deploy — ask for it.
A failed build never breaks the live site.

Cloudflare only switches the live version after a build succeeds. That is why the lock in step 5 is safe to keep: a disagreement between the page and the published folder stops the publish instead of shipping it.

Boundaries

What this does not do.

Read this before assuming the setup covers more than it does.

Not covered

The Worker API

Reminders, push notifications and the metals endpoint run in a Worker, and Cloudflare's Git connection publishes Pages only. When worker.js changes, that deploy is still a separate, deliberate action.

Not covered

Your current address

The new project gets a new .pages.dev address. Keeping the exact old one would need a custom domain attached to the new project, which is a separate piece of setup.

Deliberate

No API token anywhere

This route never asks you to create or paste a Cloudflare token, and no secret is stored in the repository. That is the main reason it is the safer of the two options.

Deliberate

The tests still run on GitHub

The full check suite already runs on every push in GitHub Actions. The Cloudflare build only checks the published folder, which keeps a push-to-live loop down to about a minute instead of several.
