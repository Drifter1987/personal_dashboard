Guide · publishing this dashboard

Ship it, then prove it actually landed.

Two things publish here, to two different Cloudflare products: the Worker API and the static page. A green deploy command proves only that an upload was accepted. This procedure ends with a check that asks the live site which build it is serving — and fails if the answer is older than the tree you just shipped.

Before you start

What has to be true first.

Two of these are the reason a publish goes to the wrong place or dies halfway. Checking them costs a minute; discovering them at step 6 costs a release.

  • A terminal in the repository root, with node 18 or newer — the smoke test uses fetch and AbortSignal.timeout.required
  • Python 3 on PATH — the gate's bundle check shells out to _zip.py to compare CRCs.required by the gate
  • A Cloudflare credential for the hosting account, and the user's explicit agreement to publish with it.ask first, always
  • Reachability to the third parties the harness reads: ECB, Yahoo, CoinGecko, IMF, the news feeds.gate only
  • About 5 minutes, most of it the gate. The uploads themselves take under 30 seconds together.time
The account is a decision, not a default.

A Pages deploy carries no account binding in config — the credential alone decides where the page lands. Three Cloudflare accounts exist on this machine, so the account is named out loud at step 1, before anything is written. Nothing in this guide should be run against an account the user has not chosen.

What the gate actually proves.

Three things, and no more: the shipped page and Worker pass the harness against real sources; the artifact about to be published is byte-identical to the artifact that was tested; and, when a release tag points at the current commit, that tag names the version the page carries. It does not publish, and it does not prove the live site changed — that is step 6.

The procedure

Eight steps, in order.

Each step ends with something you can see. If a verify condition does not hold, stop there: every later step assumes the previous one is true.

Progress 0 / 0
  1. 20 sec

    Name the account you are about to publish to

    Neither deploy pins an account in config. The credential does, so this is the step that decides where everything lands.

    npx --yes wrangler@4.151.3 whoami

    You should see the email and a single account row — on this machine, drifter_87@live.com and 8660293d…. If the email is not the account the user named, stop and fix the credential before anything is written.

    If it says you are not logged in

    Run npx wrangler login and finish the browser flow. If a different account answers, switching credentials is a deliberate action with its own backup procedure — see the account inventory rather than overwriting the token in place.

  2. 2 min

    Run the gate

    Nothing is published until this exits 0. It is the only step that runs the Worker and the page against the real sources before an upload exists.

    node _deploy.mjs

    You should see a wall of PASS lines ending in RELEASE READY: the page, the Worker and dashboard-site.zip agree, and the harness is green. and an exit code of 0. The last recorded run of this harness, on 2026-10-22, printed 306 checks; the total grows with every release, so read it as what passed, not as a target.

    If exactly one chart/live check fails with an HTTP status

    That is a third party, not your change. The harness reads CoinGecko, Yahoo and the ECB for real, and a throttled public API shows up as no data returned (Yahoo HTTP 404) or similar. Re-run the gate once before believing it — this exact failure appeared twice on 2026-10-21 and cleared on its own.

  3. 10 sec

    Let the gate repair the bundle, if it said to

    The hosted copy is not the source file: the gate pins the page's one inline script by hash, which is what lets the CSP drop unsafe-inline. A stale bundle is the single most common reason a correct edit never reaches the site.

    node _deploy.mjs --sync

    You should see wrote deploy\index.html - index.html with its script pinned (1 hash), then bundle repaired and a second green bundle pass that names this tree's bundle, be2bbab4e756, with script … · no 'unsafe-inline' beside it.

Phase two · publish

  1. 20 sec

    Deploy the Worker with its build tag

    The version string cannot identify a build: 1.14.0 went out more than once with different code. The tag is the first 16 characters of the sha256 of worker.js, and /api/health reports it back so step 6 can tell an older Worker from this one.

    npx --yes wrangler@4.151.3 deploy --tag "$(node _smoke.mjs --worker-tag)"

    You should see the binding table including env.CF_VERSION_METADATA … Worker Version Metadata, then Uploaded home-dashboard-api and Current Version ID: …. The id changes on every deploy; the tag is what step 6 compares.

    If the deploy is rejected because of the tag

    Print it on its own first: node _smoke.mjs --worker-tag returns 16 lowercase hex characters. A nested quoting mistake in the shell is far more likely than the tag being invalid.

  2. 10 sec

    Publish the page

    The page is a separate Cloudflare product with its own upload. Deploying the Worker does not move it, and vice versa.

    npx --yes wrangler@4.151.3 pages deploy deploy --project-name home-dashboard --branch main --commit-dirty=true

    You should see Deployment complete! Take a peek over at https://<hash>.home-dashboard-5ma.pages.dev. That hash is new on every upload — worth copying if you want to inspect that exact deployment, compared by nothing later.

    If it uploads but the production URL does not change

    Check the branch flag. The production branch is main; deploying to another branch publishes a preview URL and leaves home-dashboard-5ma.pages.dev exactly where it was.

Phase three · prove it

  1. 15 sec

    Ask the live site which build it is

    This is the whole point of the guide. A successful upload is not a successful publish, and an edge can serve the previous deployment for a few seconds after one.

    node _smoke.mjs

    You should see SMOKE PASSED: … serves the tested bundle <hash> (v2.30.5), all 8 files match, and the Worker serves this tree's worker.js (build <tag>), exit code 0 — for this tree, bundle be2bbab4e756 and build de3c4bd21b37e087.

    If it fails, read which half failed

    the live Worker reports no build tag — the Worker went out without --tag; repeat step 4. live tag … is not the source here — an older or different Worker is live. live v… is older than the shipped v… — the page publish did not land on this origin. Each message prints the exact command that fixes it.

  2. 1 min

    Accept the update in your own browser

    A deploy cannot reach inside a service worker. Clients keep the cached shell until they take the prompt — which is why a perfectly correct deploy can look like nothing happened.

    Open the dashboard, wait for the bar reading A new version is ready — reload to use it., and press Reload.

    You should see the browser tab read Home Dashboard v2.30.5 — the shell this release ships — and the bar gone after the reload. A tab still showing a previous version number is the cached shell, not this build.

    If no bar ever appears

    The shell did not change, or the worker's cache name did not. deploy/sw.js keys its cache on VERSION plus SHELL_REV; an HTML-only change with neither bumped installs nothing. Bump SHELL_REV, re-sync, and publish the page again.

  3. 1 min

    Check it from outside the CLI

    The smoke test is code you could have broken. Two curl-shaped facts, taken by hand, are the independent second opinion.

    # 1. the Worker's own answer
curl -s https://home-dashboard-api.drifter-87.workers.dev/api/health

# 2. the page bytes against the tested bundle
curl -s https://home-dashboard-5ma.pages.dev/ -o /tmp/live.html
cmp -s /tmp/live.html deploy/index.html && echo "live == tested bundle"

    You should see "ok":true, "build":"<tag>" and "keyResolved":true in the JSON, and live == tested bundle on its own line. If cmp says nothing and exits 1, the edge is still on the previous copy.

Short version

If you already know this.

The same procedure with the reasoning removed. It is not a summary — every command is the one from above.

  • whoami — confirm the email and account id, out loud.
  • node _deploy.mjs — stop on anything but RELEASE READY.
  • node _deploy.mjs --sync — when the bundle is reported stale.
  • wrangler deploy --tag "$(node _smoke.mjs --worker-tag)".
  • wrangler pages deploy deploy --project-name home-dashboard --branch main.
  • node _smoke.mjs — exit 0 or you are not done.
  • Press Reload on the update bar in the browser you actually use.

Never route around a red gate.

--page-only exists for the CI job that publishes the page and nothing else. Using it by hand to dodge a failing Worker check is how a page ships against an API that was never deployed — the exact failure the build tag was added to catch.

Rollback, in one line each.

Worker: wrangler deployments list, then wrangler rollback <version-id>. Page: republish the previous known-good deploy/ bundle, or roll back in the Cloudflare dashboard. Both are documented in DEPLOY.md §5 and neither was run on this page's date — treat them as documented, not tested here.

Boundaries

What this does not do.

Read before trusting a green run to mean more than it does.

Not covered

Cutting a release

Nothing here bumps a version, writes release notes or creates a tag. That is node _release.mjs plus the changelog, and a versioned release is a different procedure with its own gate.

Not covered

The CI publish path

Pushing a v* tag publishes the page automatically. That path is described in the publishing guide; this page is the by-hand route and the one to use when the pipeline itself is what is broken.

Partial

What a second device sees

Step 7 updates one browser profile. The verification cannot see another phone's service-worker cache, a CDN in another country, or an installed app that has not been opened since the deploy.

Partial

The Worker, from CI

The automated publish job runs _smoke.mjs --page-only, so it checks the page and not the API. A release that changes only worker.js is verified by hand or not at all.

Not covered

The other two accounts

Everything here assumes the main hosting account. The legacy client account and the empty one have their own projects and are never the target of these commands.

Not covered

Secrets and bindings

This guide never sets a key. Deploys preserve the declared bindings in wrangler.toml, but rotating a secret or adding a binding is its own action with its own consent step.

How current is this?

Walked on 2026-10-21 with wrangler 4.151.3 on Windows 11. The versions, the build tag, the bundle hash, the file count and the step count are read from this tree by node _guide.mjs, so they describe the build these steps ship rather than the run they were written from; node _deploy.mjs re-reads them and refuses a tree whose page names a build the files have moved past. The commands and the verify conditions are held to the scripts by node _check.mjs in the same way, and the gate reads live third parties, so its runtime depends on them.
